- 기준: Claude 다중 계정 배포 이후 main `ba704bd`. 화면·리포트를 검토한 제안 전체를 사용자가 승인했고 권장 순서대로 진행한다.
- 순서: (1) 빠른 수정 묶음 → (2) 한도 활용 리포트·소진 시 다른 계정 잔여 → (3) Codex 계정 합계 차이 분리·차트 색·달력 색 단계 → (4) 한도 요약 목록·상태 탭·요약 카드 → (5) 월간 정산·주중 비교·주간 리포트 확장·초기화 전 미사용 알림 → 운영 배포 1회.

## 1단계: 빠른 수정 묶음

### 구현

- 일시 실패 칩: `/api/usage` 소스 행에 마지막 성공 시각(`source_health.last_success`)을 붙였다. 상단 알림 칩은 성공 기록이 없거나 마지막 성공 후 30분이 지난 실패만 띄운다(외부 알림의 30분 기준과 같음). 수집 상태 탭은 실패를 즉시 보여 준다. 운영 행(수집기·일일 백업·원본 대조)의 실패 칩이 두 번 나오던 중복도 없앴다.
- 계정 이름: 알림 칩의 소스 이름을 `claude-oauth · Max 5x` 형식으로 쓰고, 계정 접미사가 붙은 `claude-oauth:<계정>`의 수집 지연도 칩으로 잡는다. 한도 이력의 출처 문구도 계정 접미사를 떼고 ‘계정 조회’로 표시한다. 외부 알림의 ‘수집 실패 지속’ 제목도 같은 계정 이름을 쓴다(`claude_accounts.source_label`).
- 구독 가치: 구독 행에 기간 토큰(`period_tokens`)을 추가했다. 기간에 토큰이 없으면 ‘기간 내 사용 기록 없음’, 토큰은 있으나 단가가 없으면 ‘기간 내 미산정’으로 구분한다. 여러 Claude 계정은 단가가 없어도 계정별 토큰을 센다. 보완 합계(Codex 계정 합계 차이·Claude 클라우드)도 그 구독의 기간 토큰에 더하고, 선택 기간 경계에 걸친 합계만 있으면 ‘사용 없음’으로 단정하지 않고 미확정(`null`, 화면은 ‘기간 내 미산정’)으로 둔다.
- 원시 키: 초기화권 대상처럼 버킷 키만 있는 곳도 `seven_day_overage_included` → ‘추가 포함량 주간’, `seven_day_<모델>` → ‘<모델> 주간’으로 읽는다. Antigravity의 이름 있는 한도 풀(`gemini-argon-wtu-weekly`)은 주간 묶음 안에 ‘Gemini argon-wtu’로 표시한다(제공사가 준 풀 이름 그대로, 의미를 추정하지 않음). 외부 알림 제목도 같은 규칙이다.
- 숫자: 자원 금액은 소수 둘째 자리까지(원·엔·횟수·100 이상 크레딧은 정수)로 줄이고 정확한 값은 툴팁에 둔다. 히트맵 요약·달력 통계는 축약 숫자와 정확한 값 툴팁을 쓴다.
- 모바일 주간 리포트 표: 390px에서 서비스 짧은 이름을 쓰고 요청 열을 숨긴다.
- 세션 ID: 앞 8자가 같은 ID(같은 시각에 만든 UUIDv7 등)를 구분하도록 앞 8자와 끝 4자를 보이고 전체 ID는 툴팁·복사 버튼에 둔다.

## 2단계: 한도 활용 리포트와 다른 계정 잔여

### 구현

- 한도 이력 구간 나누기(`insights.segment`)를 `quota_history`에서 분리해 주간 리포트와 같이 쓴다. 동작은 그대로다.
- `reports.quota_use`: 주마다 한도 창별로, 소진 횟수와 같은 관측 흐름 하나를 골라 계산한다. 그 주에 가장 오래 관측한 흐름을 쓰고, 같으면 계정 조회를 쓴다.
  - 관측 시간: 10분 이내로 이어진 연속 관측 구간의 합. 두 관측 사이에 수집 실패가 기록된 구간은 뺀다.
  - 0% 시간: 이어진 두 관측이 모두 0%인 구간의 합.
  - 초기화 직전 잔여: 창의 초기화 시각이 이어진 두 관측 사이에 지나간 경우만 직전 관측값을 센다(새 창이 1분 일찍 보이는 시계 차이는 허용). 관측 없이 지나간 초기화는 추정하지 않는다.
  - 현재 계정 이전 관측은 제외하고, 1분 미만 관측된 창은 뺀다.
- 운영 DB 사본에서 첫 구현을 돌려 보니, 쓰지 않는 Antigravity 5시간 창은 조회마다 초기화 시각이 5시간 뒤로 밀려 한 주에 ‘초기화’가 1,884회로 잡혔다. 또 Claude 5시간 창은 끝난 뒤 새 창이 없으면 초기화 시각 없이 와서 실제 초기화를 놓쳤다. 그래서 초기화 판정을 ‘연속된 두 관측 사이에 초기화 시각이 지났는가’로 바꿨고, 두 경우 모두 회귀 테스트를 추가했다.
- 리포트는 만들 때 한도 활용·소진 횟수를 저장한다(`quota_use`). 한도 이력은 보존 기간(기본 30일) 뒤 지워진다. 기존 코드는 단가 변경 등으로 지난 리포트를 다시 만들 때 소진 횟수를 빈 목록으로 덮어썼다(재현 확인). 이제 이력이 지워진 주는 `None`으로 두고 이전에 계산한 값을 유지한다. 처음부터 이력이 없는 주는 0이 아니라 ‘계산하지 않음’으로 표시한다.
- 연속 소진: 저장된 이전 주 리포트를 거슬러 올라가 같은 창의 소진이 이어진 주 수를 센다. 빠진 주가 있으면 끊는다. 재작성은 오래된 주부터 한다.
- 화면: 주간 리포트에 ‘한도 활용’ 표를 추가했다(한도·소진·0% 시간·초기화 직전 잔여·관측). 2주 이상 이어진 소진에는 `N주 연속 소진` 배지를 붙인다. 휴대폰에서는 관측 열을 숨기고 이름·직전 잔여 칸만 줄바꿈한다. 이 필드가 없는 이전 리포트는 기존 소진 줄을 유지한다.
- 외부 알림의 주간 리포트 요약에 연속 소진 주와 0%로 머문 시간 상위 3개를 넣었다.
- 다른 계정 잔여(F1): Claude 계정 하나의 창이 소진되면 상단 칩과 외부 ‘소진’ 알림에 같은 창의 다른 계정 최신값을 덧붙인다. 대시보드는 `format.js`의 `otherAccounts`, 알림은 `notify.other_accounts`로 같은 규칙을 쓴다. 계정 미확인·오래된 값은 빼고, 막힌 창은 ‘사용 불가’로 표시하며, 전환 권유 문구는 넣지 않는다.
- Codex 계정 합계 차이(자동 리뷰) 비중은 이름 설정이 생기는 3단계에서 리포트에 넣는다.

### 구현

- 집계(`reconciliation.apply`): 계정 일별 합계에서 이 PC 기록을 뺀 보완분은 모델·프로젝트 묶음에서 예약 키 `/account-residual` 한 항목이 된다(`/`가 들어 있어 디렉터리 이름에서 오는 프로젝트명과 겹치지 않는다). 전에는 모델 `unknown`, 프로젝트 `미분류`에 섞였다. 합계·누계·시계열·비교·달력·히트맵·비용 범위는 그대로이고, 행·합계에 `residual_tokens`를 더해 이 몫을 따로 알린다. 범위 좁히기 목록(모델·프로젝트)에는 넣지 않는다.
- 프로젝트 월 합계(`project_month`)와 프로젝트 상세는 이 몫을 `미분류`에서 빼고 `residual_tokens`로 따로 둔다. 프로젝트 예산 계산에는 들어가지 않는다.
- 이름: 설정의 구독 구획에서 정한다(`residual_label`, 20자 이하, 제어 문자 불가, 비우면 기본값). 공개 기본값은 ‘로컬 미기록’이고 운영 설정은 배포 때 ‘자동 리뷰’로 둔다. 이름은 화면 설정이라 캐시되는 사용량 본문이 아니라 `/api/usage` 응답 층에서 붙인다.
- 화면:
  - 모델 표: 순위 없이 맨 아래 행(‘계정 합계 − 이 PC 기록 · 모델 구분 없음’). 정렬과 무관하게 마지막이며 CSV도 같은 순서·이름이다. 행을 눌러도 범위가 바뀌지 않는다.
  - 모델 순위: 순위에서 빼고 비중은 모델이 기록된 사용량 기준으로 계산한다(캡션에 표시). 아래에 회색 줄로 토큰과 ‘전체의 N% · 순위 제외’를 보여 주며, 요청 수·비용 지표에서는 값이 없으므로 ‘—’와 막대 없음.
  - 토큰 구성: ‘내역 미분류’(다른 분류 없는 보완분)와 나눈 회색 항목. ‘{이름} 제외’ 토글(기본 켬)로 고리에서 빼고 목록에는 ‘차트 제외’로 남긴다. 둘 다 빼면 중앙에 ‘2개 항목 제외’, 접근성 이름에는 두 항목을 모두 적는다. 제외 항목만 있는 기간은 ‘사용 기록 없음’ 대신 제외 안내를 보인다.
  - 프로젝트 표: 맨 아래 행, 상세 버튼과 범위 좁히기 없음. 로컬 기록의 `미분류` 프로젝트는 그대로 남는다.
  - 차트: 모델·프로젝트 묶음에서 이름으로 된 별도 계열이다. 프로젝트처럼 항목이 많아 상위 7개와 ‘기타’로 줄일 때도 ‘기타’에 접지 않는다. 일별 간격에서는 계정 하루(KST 09:00–다음 날 09:00)가 자정을 넘으므로 기존처럼 날짜 미배분이다.
  - 상태 탭의 ‘Codex 계정 합계 대비 …’ 제목·열과 설명이 같은 이름을 쓴다.
- 범위 좁히기: 모델·프로젝트 범위(`unknown`·`미분류` 포함)에는 이 몫을 넣지 않는다. 전에는 모델·프로젝트가 없는 보완분을 `unknown`·`미분류`로 간주해 ‘미분류’ 프로젝트로 좁히면 다시 섞였다. Codex 서비스·OpenAI 제작사 범위에는 그대로 들어간다.
- 주간 리포트: 계정 일별 합계가 주 안에 온전히 든 날(월~일 주는 최대 6일)만으로 이 차이와 계정 합계 대비 비중(`residual`)을 저장한다. 그런 날이 없으면 줄을 만들지 않는다(0%로 채우지 않음). 상위 모델에서는 뺀다. 화면과 외부 알림 요약(수집기가 설정의 이름을 넘김) 모두 같은 줄을 쓴다.
- 저장된 리포트: 리포트 내용 형식 번호(`REPORT_FORMAT=2`)를 재작성 판단 값에 넣어, 배포 후 저장된 주(최대 12주)를 한 번 다시 만든다. 전에는 기록·보완분·단가가 바뀔 때까지 이전 리포트가 이 몫을 상위 모델 `unknown`으로 보였다. 다시 만든 주는 알림을 다시 보내지 않고, 이력이 지워진 주의 소진·한도 활용은 2단계의 유지 규칙대로 남는다.
- 이름이 도착하거나 바뀌면 이미 그린 주간 리포트를 다시 그린다(리포트 목록은 5분 동안 다시 받지 않으므로).

## 4단계: 한도 탭 압축, 상태 탭 문제 먼저, 기간 요약 카드

### 구현

- 한도 탭(PC, 601px 이상): 창마다 한 줄 격자(이름·잔여·막대·초기화까지 남은 시간·상세)로 바꿨다. 남은 시간은 폭을 고정해 막대 끝을 맞추고, `초기화 … 후` 대신 카드 머리의 ‘잔여 · 초기화까지’ 아래에 `4일 15시간`만 쓴다(모바일 카드는 `초기화 4일 15시간 후`). 메모·감소량·주간 소진 안내·펼친 상세는 그 아래 전체 폭에 둔다. 카드 열 수는 서비스 수(`data-cards`, 최대 3열; 1120px 이하 2열, 820px 이하 1열)를 따른다. 예전에는 휴면 접힘이 모든 열을 차지해 auto-fit 빈 열이 접히지 않았다.
- 현재값(`fresh`)에는 상태 배지를 달지 않는다. 오래된 값·미제공·수집 실패·구독 종료·잔여 적음·주간 소진만 표시한다. 감소량 줄은 0.1%p 이상 감소했을 때만 보이고, 관측된 0은 그 창의 상세에 같은 문구로 남긴다(관측 부족은 어디에도 표시하지 않음). 모바일 목록은 그대로이고, 모바일 상세 카드도 같은 배지·감소량 규칙을 따른다.
- 상태 탭: 요약을 `실패·확인 필요·미제공·미사용·정상` 순서로 바꿨다(0이면 색 없음). **조치 필요**(실패·일부 미수집·오래된 값)는 카드로 먼저, **지금 수집하지 않는 경로**(미제공·미사용·구독 없음)는 중립색 목록으로 늘 펼쳐 둔다. 상태줄을 받지 못하는 상태를 숨기지 않는다는 기준 때문에 접지 않았다. 정상 수집원은 서비스별(내부 작업 포함)로 접고, Codex 계정 합계 차이 표와 수집 범위 설명도 접는다. 펼침 상태는 자동 갱신 뒤에도 유지한다.
- 한 번만 실행하는 세션 귀속 백필(`session-backfill`)은 완료 기록이 시간이 지나 `오래된 값`이 되어 조치 필요에 섞였다. 서버의 시간 기준 오래됨 판정에서 뺐다(`ONE_TIME_SOURCES`).
- 기간 요약: 전체 토큰 → 비용 추정 → 일반 입력·캐시 읽기·출력 순서로 바꿨다. API `prior`는 직전 같은 길이 구간(비교를 고르면 7일·28일 전)을 진행 중인 기간과 같은 경과 시점까지 잘라 요청 기록 합계·비용을 담는다. 보완 누계는 양쪽 모두 그 시점까지 끝난 것만 센다(`current_tokens`, `prior`). 마지막 조회 시각까지로 잘린 진행 중 Codex 계정 하루(`running`)는 기간 합계에는 들어가도 비교에서는 뺀다. 같은 시각의 계정 하루를 양쪽에서 똑같이 빼서 하루 차이로 증감이 부풀지 않는다. 비교에 들어간 자료 중 하나라도 비교 구간 시작 뒤에 시작하면 `complete=false`로 두고 화면은 `기록 부족`을 쓴다. 이 PC 기록은 어느 쪽에든 있을 때만 첫 기록 시각을 보고, 보완 누계는 출처별 첫 보완 구간 시각을 본다. 사용 0이면 `사용 없음`, 두 배부터 `3.2배`, 100배 이상은 `100배 이상`으로 쓴다. 비교 필터의 `compare.elapsed`는 기존 그대로 둔다.

### 리뷰

- 자동 리뷰 1회차 지적 1건(P2) 반영: 비교 완전성을 이 PC 기록의 첫 시각만으로 판단해, 이 PC 기록은 오래됐지만 Codex 계정 합계가 이번 구간부터 있으면 직전 구간의 계정 몫이 0으로 취급되어 증감이 부풀 수 있었다. 계정 합계만 있는 기록은 반대로 `기록 부족`이 됐다. 비교에 들어간 출처마다 직전 구간 시작 전부터 자료가 있는지 보도록 바꾸고, 두 경우를 실패부터 확인한 테스트로 추가했다. 운영 DB(읽기 전용 조회)에서는 계정 합계·클라우드 보완 자료가 7일·30일 비교 구간보다 앞서 시작해 이 규칙으로 `기록 부족`이 되지 않는다. 공용 브라우저 데이터는 계정 합계가 최근 3일뿐이라 7일 비교가 `기록 부족`이 맞으므로, smoke는 그 문구를 확인하고 숫자 증감은 Claude Code 범위에서 확인한다. 아무 사용도 없는 범위는 `사용 없음`(완전함, 양쪽 0)이다.
- 자동 리뷰 2회차 지적 2건(P2) 반영:
  - 끝난 Codex 계정 하루가 계속 진행 중으로 취급될 수 있었다. 같은 합계가 다시 오면 처음 받은 시각을 보존하는데, 그 시각이 하루가 끝나기 전이면 이후에도 진행 중으로 판정되어 비교 양쪽에서 빠졌다. 이제 수신 시각이 아니라 계정 하루(09:00~다음 날 09:00) 전체가 각 쪽의 기준 시각 전에 끝났는지로 판단한다. 기준 시각에 아직 열린 하루는 양쪽 모두에서 빠진다.
  - 출처별 자료 시작을 잔여분이 남은 항목이 아니라 실제로 받은 자료의 시작으로 본다. 이 PC 기록과 정확히 일치해 잔여분이 없는 오래된 계정 하루도 자료 범위에 든다. 1회차에 적은 ‘운영 DB에서는 이 규칙으로 기록 부족이 되지 않는다’는 자료 시작일만 보고 판단한 것이었다. 운영 DB 사본(읽기 전용 백업 API 복사)으로 실제 계산하니 30일 카드가 이 문제로 `기록 부족`이었고, 수정 후에는 비교가 표시된다. 7일 카드 값은 수정 전후가 같았다. 사본은 확인 후 삭제했다.
  - 두 경우 모두 이전 코드에서 실패하는 테스트를 먼저 확인했다.
