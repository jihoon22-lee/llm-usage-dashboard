# 시나리오 기반 코드·사용성 리뷰

검토 기준: main `b56750d`, 2026-10-09 KST. 요청 범위는 상세 리뷰와 테스트 환경 검증이다. 제품 코드 수정·운영 배포는 수행하지 않았다.

기존 회귀 검사는 통과했지만, 추가 사용 시나리오에서 수정할 문제 7건을 재현했다. 우선순위는 모두 **P2(일반 수정 필요)**이며, 이번 범위에서 P0/P1 문제를 확정하지 않았다. 입력 유실, 잘못된 기간의 데이터 표시, 복구할 수 없는 설정 흐름을 먼저 수정하는 것이 좋다.

## 검증 환경과 범위

- 독립 worktree와 uv 0.12.23의 `uv sync --locked`로 생성한 개발 가상환경. Python 3.14.7, Playwright 1.63.0, Chromium headless, Node 24.18.0.
- 임시 SQLite DB, 가상 제공사·모델·세션 기록, Flask test client, 실제 HTML/CSS/JavaScript와 운영 CSP를 사용했다. 브라우저 요청을 해당 Flask 응답으로 연결하고 필요한 경우에만 400/503/연결 실패/응답 지연을 주입했다.
- 데스크톱 1440px, 태블릿 768px, 모바일 390/320px에서 실제 브라우저로 조작했다. 화면 크기 재현이며 실제 휴대폰·Safari 검증은 아니다.
- 운영 DB·설정·서비스·가상환경을 변경하지 않았으며 실제 제공사 계정 조회와 수동 수집은 실행하지 않았다. 수동 갱신은 UI와 합성 완료/대기 응답만 검증했다.
- 처음 실행한 일부 검사는 샌드박스의 소켓/Chromium 실행 제한으로 실패했다. 허용된 독립 환경에서 재실행한 최종 결과는 아래와 같다. 이는 제품 실패와 구분한다.

## 수정 필요 사항

### R1 · P2 · 한 행 저장 또는 일부 저장 실패가 다른 미저장 입력을 버림

코드: [settings.js](../llm_usage/web/settings.js) 108~125행, 특히 115·124행의 `loadConfig()`와 43~76행의 전체 입력 재생성.

재현: 설정에서 `gpt-test` 입력 단가를 7.25, `claude-test`를 8.75, Codex 구독료를 99로 바꾼 다음 `gpt-test` 행의 저장만 누른다. 저장하지 않은 두 입력이 서버의 2와 20으로 즉시 돌아간다. 일괄 저장에서 한 행에 10001을 넣으면 서버 검증 실패 후에도 전체를 다시 그려 실패 행의 입력·dirty 상태가 사라진다.

영향: 여러 항목을 검토하며 편집하는 사용자가 값을 다시 찾아 입력해야 한다. 개별 저장 버튼이 다른 영역까지 초기화한다는 안내가 없어 변경 내용을 모두 저장했다고 오해할 수 있다.

수정 방향: 저장 성공한 행만 새 값으로 확정하고 나머지 draft를 유지한다. 일괄 저장에서는 성공/실패 행을 따로 표시하며 실패 입력과 재시도 동작을 보존한다. 정상 온라인 편집 상태의 보존 문제이며, 연결 단절 시 비밀 설정을 비우는 기존 정책과는 분리해서 처리한다.

완료 조건: S1에서 다른 단가·구독료 draft와 dirty 표시가 유지된다. S2에서 성공 행은 저장되고 실패 행은 입력값·오류·재시도 버튼을 유지한다.

### R2 · P2 · 비워 저장한 구독료를 웹에서 다시 설정할 수 없음

코드: [settings.js](../llm_usage/web/settings.js) 43~46행. 보조 원인: [store.py](../llm_usage/store.py) 840~848행에서 `subscriptions`도 설정된 구독료 목록만 순회한다.

재현: Codex 구독료 입력을 비움 → 저장 → 통계 갱신 완료 → 다른 탭으로 나갔다 설정 재진입. `scope_options.route`에는 Codex가 남아 있지만 `input[data-route="codex"]`는 0개가 된다.

영향: UI가 안내하는 ‘비우면 미설정’ 동작을 한 번 사용하면 재입력이 막힌다. 새로 사용하기 시작했으나 아직 구독료가 없는 서비스에도 같은 목록 구성 문제가 적용된다. 설정 파일이나 API를 직접 수정해야 복구할 수 있다.

수정 방향: 편집 가능한 서비스 목록을 금액 유무와 분리한다. 관측한 route·지원 서비스 목록·저장된 설정의 합집합으로 입력을 유지하고 미설정 값을 빈칸으로 표시한다.

완료 조건: S12에서 빈 값을 저장하고 새로고침해도 Codex 입력칸이 남아 있고, 새 금액 저장 후 구독 가치 계산에 다시 포함된다.

### R3 · P2 · 느린 인사이트 요청 중 필터를 바꾸면 최신 요청을 잃음

코드: [app.js](../llm_usage/web/app.js) 9~15행.

재현: 개요에서 인사이트로 들어가 7일 인사이트 응답을 보류한다. 소비 분석으로 이동해 기간을 오늘로 바꾸고 core 갱신을 완료한다. 다시 인사이트로 들어간 다음 앞서 보류한 7일 응답을 전달한다.

실제 결과: `insightsPending`이 쿼리 구분 없이 이전 Promise를 재사용한다. 이전 응답은 쿼리가 다르므로 버려지지만 최신 요청을 다시 시작하지 않는다. 네트워크상 인사이트 요청은 7일 1건뿐이며, `lastUsage`에는 insights가 없고 프로젝트 표는 ‘불러오는 중…’에 머문다.

영향: 느린 Tailscale 연결에서 자연스럽게 탭과 필터를 바꾼 사용자가 무한 로딩으로 인식한다. 다음 갱신이나 재진입까지 스스로 회복하지 않는다.

수정 방향: 인사이트 요청을 쿼리 키와 함께 관리한다. 쿼리가 달라지면 별도 요청을 시작하거나 최신 요청을 예약하고, 완료 시 최신 쿼리가 아직 미충족이면 다시 요청한다.

완료 조건: S11의 응답 순서에서 ‘오늘’ 인사이트 요청이 실제로 발생하고 최신 표가 렌더링된다. 늦게 끝난 이전 요청이 새 상태를 덮어쓰지 않는다.

### R4 · P2 · 인사이트 로딩 실패 시 이전 기간의 표가 새 기간 데이터처럼 남음

코드: [app.js](../llm_usage/web/app.js) 14행, [insights.js](../llm_usage/web/insights.js) 64행의 이전 세션 표 보존과 155행의 이전 프로젝트 표 보존.

재현: 7일 인사이트를 본 뒤 소비 분석에서 오늘로 변경한다. 오늘 core 응답은 성공시키고 인사이트 요청만 503으로 실패시킨다.

실제 결과: 상단 필터는 ‘오늘’이지만 프로젝트 표는 기존 7일의 21요청·27,930토큰을 유지한다. 오류는 아래쪽 데이터 신뢰도 패널에만 들어가며 전역 오류 배너는 숨겨져 있다. 모바일에서는 해당 패널이 접혀 있어 오류를 찾기 더 어렵다.

영향: 사용자는 요청 실패보다 잘못된 기간의 소비량을 믿는 문제가 생긴다. 표 근처에는 어느 조건에서 받은 사본인지 안내가 없다.

수정 방향: 필터 변경 시 패널 데이터의 쿼리 키를 확인하고, 새 데이터가 없으면 로딩/실패 상태로 전환한다. 이전 결과를 유지하려면 이전 기간·사본임을 해당 패널에 명시하고 재시도를 제공한다. 별도로 S4의 캐시 대체 경로에서도 오프라인 표시를 즉시 갱신해야 한다. 현재 오프라인 표시는 `updatedText()` 호출까지 지연된다.

완료 조건: S3에서 ‘오늘’이라는 문맥 아래 7일 표를 정상 결과처럼 표시하지 않는다. 데스크톱과 모바일 접힘 상태 모두 오류·재시도를 식별할 수 있다. S4에서 캐시 사용 즉시 사본 안내가 보인다.

### R5 · P2 · 응답이 멈추면 90초 수집 제한도 작동하지 않고 갱신이 잠김

코드: [core.js](../llm_usage/web/core.js) 78~92행, [app.js](../llm_usage/web/app.js) 61~67행.

재현: 초기 화면을 정상 로드한 뒤 `/api/usage` 또는 수동 수집 후 `/api/collection`의 fetch가 resolve/reject하지 않도록 지연한다. 브라우저 가상 시계를 120초 진행한다.

실제 결과: 두 경우 모두 갱신 버튼 disabled·aria-busy=true, 오류 안내 없음. 수동 갱신의 deadline은 `await api('/api/collection')` 바깥에서만 검사해 해당 await가 멈추면 제한을 적용할 수 없다. 이 재현은 실제로 120초를 기다린 네트워크 실험이 아니라, 완료되지 않는 요청과 가상 시계로 애플리케이션 시간 제한을 검증한 것이다.

영향: 연결이 즉시 실패하지 않고 멎는 환경에서는 UI로 재시도할 수 없고 새로고침해야 한다. 후속 필터 변경도 기존 pending에 묶인다.

수정 방향: fetch와 응답 본문 읽기에 요청 제한·취소를 적용하고 전체 수집 대기 deadline의 잔여 시간을 개별 조회에도 반영한다. 수집 POST가 이미 접수되었을 수 있으므로 취소/재시도를 실제 수집 취소와 혼동해 안내하지 않는다.

완료 조건: S5/S6에서 정해진 시간 안에 실패 안내와 재시도 동작이 복구된다. 늦은 응답이 최신 필터의 결과를 덮어쓰지 않는다.

### R6 · P2 · 비용 추이 CSV가 미산정을 0으로 내보냄

코드: [analysis.js](../llm_usage/web/analysis.js) 39~44행, 281행의 `metricValue`.

재현: 단가가 있는 모델과 없는 모델을 함께 기록한다. 미등록 모델에 1,000,020토큰을 넣고 소비 분석에서 모델별·비용 추정으로 바꿔 ‘사용 추이’ CSV를 저장한다.

실제 결과: API series는 `cost: 0, unpriced: 1000020`으로 숫자와 미산정 정보를 함께 제공한다. CSV는 cost 숫자만 내보내 해당 모델 비용을 `0`으로 기록하고 미산정 토큰/상태를 버린다. 화면 툴팁의 `+미산정` 안내도 CSV에는 없다.

영향: 다운로드한 파일에서는 무료 사용·사용 없음·단가 미확인을 구분할 수 없다. 사용자가 합계를 비교하거나 공유할 때 부분 비용을 전체 비용으로 해석할 수 있다.

수정 방향: 완전 미산정은 빈 값/미산정으로 표시하고 부분 산정은 산정된 비용과 미산정 토큰 또는 산정 범위를 함께 내보낸다. 합계에도 부분 산정 여부를 보존한다.

완료 조건: S7 CSV만으로 단가 확정 0원과 미산정을 구분할 수 있다. 단가가 일부만 있는 서비스별 그룹도 누락 정보를 유지한다.

### R7 · P2 · 모바일 알림 설정이 세로 글자로 무너지고 좁은 화면에서 넘침

코드: [style.css](../llm_usage/web/style.css) 314~320행.

재현: 폭 390px와 320px에서 설정 → ‘알림 · 자동 갱신’을 연다. 해당 패널은 기본적으로 열린다.

실제 결과: `.cfg-row > span`의 최소 폭 150px, 줄바꿈 없는 flex 토글, 입력 폭 규칙이 겹쳐 네 알림 라벨이 각각 폭 38px·높이 102px로 배치된다. 스크린샷에서 ‘초기화 복구’, ‘수집 상태 경고’가 한 글자씩 줄바꿈되는 것을 확인했다. 320px에서는 `documentElement.scrollWidth=374`로 페이지 전체가 가로로 넘친다. 내부 테이블의 의도된 가로 스크롤과 구분한 결과다.

영향: 알림 종류를 읽고 원하는 체크박스를 선택하기 어렵다. 390px에서 문서 넘침만 검사하는 기존 smoke로는 글자 붕괴를 발견할 수 없다.

수정 방향: 모바일에서는 설정 이름과 조작 영역을 위아래로 배치하거나 토글을 2열/줄바꿈 가능한 구조로 만든다. label 내부 단어 단위 줄바꿈과 입력 폭을 함께 조정한다.

완료 조건: 320/360/390px에서 문서 가로 넘침이 없고 네 알림 이름이 자연스럽게 읽힌다. 패널을 실제로 열어 입력·체크·저장까지 검증한다.

## 추가 사용성 개선 제안

다음은 위 7건과 구분한 개선 제안이다.

- **첫 실행 안내:** S14에서 수집을 한 번도 하지 않았는데 ‘모든 기록 줄을 해석했습니다’가 표시된다. ‘아직 검사할 기록 없음’과 ‘검사한 기록에서 실패 없음’을 구분하고, 수집 상태 확인/최초 수집 안내를 연결하면 설치 직후 판단하기 쉽다. 구독료 입력 목록은 R2와 함께 개선할 수 있다.
- **입력의 접근 가능한 이름:** 단가 입력은 모델명·단가 종류를 조합한 label이 없고, 갱신 주기는 브라우저 접근성 트리에서 이름 없는 spinbutton으로 나타난다. 모델명/단위/항목이 포함된 `label` 또는 `aria-labelledby`를 제공할 필요가 있다. 실제 스크린리더 사용 시험까지 완료한 것은 아니다.
- **저장 결과의 위치와 지속성:** `cfgMsg()`는 결과를 5초 후 지운다. 모바일 긴 설정 화면에서는 변경한 행 바로 옆에 성공/실패를 표시하고 실패는 해결할 때까지 유지하는 편이 복구에 유리하다. 단가 부분 저장은 R1과 함께 처리한다.

## 후속 수정 순서와 재검증

1. R1/R2: 편집 데이터 보존과 구독료 재설정 경로.
2. R3/R4/R5: 쿼리별 요청 관리, 오래된 결과 식별, 시간 제한·재시도.
3. R6: CSV에서 미산정 의미 보존.
4. R7 및 추가 제안: 모바일 설정 배치와 최초 사용/접근성 안내.

각 수정은 해당 시나리오를 기대 동작 기준의 회귀 검사로 전환한다. 느린 요청은 응답 순서를 제어하고 실패·취소·재진입을 검증한다. 모바일은 가로 넘침뿐 아니라 라벨 배치와 실제 입력 동작도 검사한다. 이 기록의 발견 사항은 아직 수정되지 않았다.

## 범위 제한 및 작업 상태

- 이번 검토는 설정·조회·내보내기·탐색·실패 복구 흐름에 중점을 두었다. 전체 코드의 무결성 또는 모든 실제 제공사 연동을 보증하지 않는다.
- 실제 Tailscale 인증 접속, 운영 제공사 수동 갱신, 운영 원본 합계 대조, Safari/Firefox·실물 휴대폰은 이번에 검증하지 않았다. 기존 합성 검사의 통과와 실계정 검증을 구분한다.
- 기록 파일만 작업 브랜치 `docs/scenario-usability-review`에 커밋한다. 원격 push 요청이 없으므로 PR·main 병합·배포는 수행하지 않는다. 공개 main의 PR/ci-required 절차를 로컬 merge로 우회하지 않는다.
- 추가 검증용 스크립트·스크린샷·JSON·로그·임시 DB와 독립 `.venv`는 정리한다. 재현 절차와 관찰 수치는 이 파일에 남긴다. 제품 실행에 필요한 기본 checkout의 가상환경은 보존한다.
- 미병합 리뷰 기록을 보존하기 위해 이 브랜치와 리뷰 worktree는 남긴다. 기본 checkout의 main에는 변경을 만들지 않는다.


## 승인된 후속 구현과 검증

사용자는 결함 7건과 추가 사용성 개선 3건, PR/필수 CI/main 병합 및 운영 배포·실환경 확인까지 포함한 계획의 실행을 요청했다. `fix/usability-review-remediation` 독립 worktree와 uv 0.12.23 환경에서 진행한다. 기존 리뷰 기록은 발견 당시 결과이며 아래에 실제 수정 결과를 누적한다.

- R1/R2: 입력 8.75가 2로 유실되는 브라우저 실패와 subscription_routes 누락 API 실패를 먼저 확인했다. 행별 저장·잠금·실패 입력 재시도·탭 이동 중 메모리 draft 보존, 지원/관측/설정 서비스 목록을 적용했다. 새 API 검사 1개, 설정 시나리오 및 기존 개인정보 브라우저 검사를 통과했다. 일반 설정은 성공 시 전송 당시와 같은 draft만 확정하고, 연결 단절 시 모든 draft를 폐기한다.
- 이후 순서: 요청 경쟁·실패·시간 제한 → 비용 CSV → 모바일/접근성/첫 실행 → 전체 회귀/PR → 운영 검증 → 기록 PR과 정리. 운영 환경에는 아직 적용하지 않았다.
