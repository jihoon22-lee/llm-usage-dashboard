# 전체 코드리뷰와 후속 수정

## 범위와 방법

- 기준은 main `6a8d1a2`(v0.12.0에 단가 갱신을 더한 상태)다. Python 약 1만 줄과 웹 JS·CSS 약 4천 줄, 설치·배포 도구를 여섯 영역으로 나눠 독립 리뷰어가 읽었다: 저장·집계, 파생 분석·알림, 사용량 수집기, 한도·자원·기타 제공사, 웹 API·설정·배포 도구, 프런트엔드.
- 리뷰어는 저장소를 읽기만 했고, 운영 데이터·인증 파일·네트워크는 쓰지 않았다. 의심은 임시 폴더의 합성 데이터로 재현했다.
- 높은 심각도는 없었다. 지적마다 수정 전 코드에서 실패하는 회귀 검사를 먼저 확인한 뒤 고쳤다(`tests/test_review_findings.py` 17개가 수정 전 코드에서 모두 실패).

## 고친 것

### 알림과 한도
- 계정을 확인하지 못한 로컬 관측(`identity_unverified`)이 범위 정리 과정에서 표시를 잃어, 소진·잔여 알림과 작업 전망의 억제 조건이 동작하지 않았다. 관측에 기록된 표시를 범위에 유지한다.
- 방해 금지 동안 쌓인 알림이 4건을 넘으면 주간 리포트도 제목 한 줄로 줄어 본문이 전송되지 않았다. 리포트는 요약에 넣지 않고 따로 보낸다.
- 알림 전송에서 `http.client` 예외가 잡히지 않아 텔레그램 토큰이 든 요청 줄이 로그에 남고 대기 중인 알림이 사라질 수 있었다. 예외 종류만 기록하고, 토큰은 저장할 때 형식을 검사한다.
- 초기화 시각이 측정마다 1초씩 달라도 `회복` 알림이 나갈 수 있었다. 2초 넘게 달라질 때만 새 초기화로 본다.
- 관측값이 없는 경로의 `미제공` 자리 표시가 `계정·요금제 변경 전 관측`으로 분류돼 화면에서 사라졌다. 관측한 적 없는 자리는 이전 계정의 관측으로 보지 않는다.

### 단가
- 손으로 쓴 단가 파일에 `"cache_write": null`이나 문자열 값이 있으면 사용량 응답이 500이 되고 수집기의 알림·리포트 단계가 매번 중단됐다. 비어 있는 선택 단가는 무시하고, 숫자가 아닌 값이 있는 항목은 버린다. 객체가 아닌 단가 파일은 빈 것으로 읽는다.
- `gpt-5-codex-mini`처럼 등급 단어가 접미사 뒤쪽에 있으면 상위 모델 단가를 상속했다. 접미사 어디에 있든 다른 모델로 본다.
- 웹에서 단가를 처음 고치면 config 폴더의 단가 파일 전체가 DB 폴더 파일로 복사돼, 이후 config 폴더 파일을 고쳐도 반영되지 않았다. 웹 수정은 고친 모델만 기록한다.
- 입력·출력 없이 저장한 단가는 성공으로 응답하고 실제로는 무시됐다. 400으로 거절한다. 캐시 읽기·캐시 쓰기 칸을 비우고 저장하면 그 단가를 지운다.

### 리포트
- 기록이 지난주 중간에 시작해도 주간 리포트가 `전주 대비 +600%` 같은 증감을 계산했다. 지난주 전체가 기록 범위에 들어올 때만 증감을 계산한다.

### 웹 API
- 객체가 아닌 JSON 본문, 지나치게 깊은 중첩, ASCII가 아닌 CSRF 헤더, `effective_at`의 잘못된 값이 500을 냈다. 각각 400·403으로 응답한다.
- 모델·세션 이름 검사가 끝의 줄바꿈을 통과시켰다. 전체 일치로 검사한다.

### 수집기
- 값의 형식이 잘못된 레코드 하나(세션 ID 자리에 객체, NaN 시각)가 그 소스 전체의 수집을 매번 중단시켰다. 그 레코드만 해석 실패로 세고 나머지는 읽는다.
- 파일을 잠깐 읽지 못한 기록이 그 뒤 정상 수집 후에도 남아 7일 뒤 `누적 영구 실패`로 굳었다. 파일을 읽으면 지운다.
- 다른 앱의 SQLite를 읽을 때, 닫힌 WAL 데이터베이스 옆에 `-shm`·`-wal` 파일을 만들 수 있었다(쓰기 가능한 폴더에서 실행할 때). 이런 파일은 처음부터 변경 불가 모드로 연다. 쓰는 쪽이 잠근 데이터베이스는 우회해 읽지 않고 오류를 낸다.

### 화면
- 저장·테스트 요청을 서버가 JSON 오류로 거절한 경우(알림 테스트 실패 502, 저장 실패 500)까지 서버 장애로 보고 설정 화면의 입력을 모두 비웠다. 이런 응답은 그 요청의 실패로만 다룬다. 조회 응답의 5xx와 연결 실패는 지금처럼 설정을 비운다.
- 직접 고른 기간의 끝 날짜가 하루 이르게 표시됐다(`2026-11-10 ~ 2026-11-09`). KST 날짜로 계산한다.
- 모델 순위를 비용 기준으로 보면 단가 없는 모델이 `$0 · 0.0%`로 보였다. `미산정`으로 표시하고 막대를 그리지 않는다.
- `관측 중단` 접힘이 30초마다 닫혔고, 캐시 활용률의 추이 항목 선택이 갱신 때마다 처음으로 돌아갔다. 둘 다 유지한다.
- 구독료 적용 방식 선택이 탭을 다녀오면 `지금부터`로 돌아가, 저장하지 않은 구독료가 다른 방식으로 저장될 수 있었다. 저장 전 구독료가 있으면 선택을 유지한다.
- 자동 갱신 주기·가치 알림의 저장 결과 문구가 다른 패널에 있어 휴대폰에서 보이지 않았다. 해당 패널로 옮겼다.
- 서비스 워커가 `/api/…` 주소를 탭에서 직접 연 응답을 오프라인 첫 화면으로 저장했다. 대시보드 페이지만 저장한다.
- `?` 단축키 목록이 화면 아래에 있어 눌러도 보이지 않았다. 보이는 위치로 스크롤한다.
- 알림 발송 이력 목록에 맞지 않던 CSS 선택자를 고치고 쓰이지 않는 규칙을 지웠다.

### 설치·배포 도구
- 배포 후 상태 확인이 `http_proxy`를 거쳐, 프록시가 설정된 셸에서는 정상 릴리스를 실패로 보고 되돌릴 수 있었다. 프록시 없이 직접 확인한다.
- `install-hooks`가 심볼릭 링크인 `settings.json`을 일반 파일로 바꿨다. 링크의 대상을 고친다.

## 고치지 않고 남긴 것

| 지적 | 남긴 이유 |

| Codex 누적 카운터가 초기화된 직후의 첫 요청이 이전 구간 전체보다 크면 초기화를 감지하지 못해 그 차이만 기록함(원본 응답 기록이 없는 세션만 해당) | 고치려면 `last_token_usage`가 실제로 있었는지를 저장하는 열이 필요하다. DB 구조와 과거 기록 재해석이 걸려 별도 작업으로 다룬다 |
| Claude 클라우드 세션에 잘못된 항목이 하나 있으면 그 세션의 다른 항목도 저장되지 않음 | 실패는 지금도 `읽기 실패`로 보인다. 항목별 실패를 어디에 세고 언제 지울지 정해야 한다 |
| 개요가 한 번 읽은 서버 누계를 여러 조회에 겹쳐 쓰는 사이 수집기가 기록을 더하면 그 요청에서만 중복 집계 | 다음 요청에서 바로 맞는다. 조회들이 한 스냅숏을 공유하도록 바꾸는 범위가 크다 |
| 기간 경계에 걸친 계정 누계가 먼저 처리되면 구독의 기간 토큰이 빈 값이 됨 | 화면 표시는 같고 단가 없는 구독의 월 결산 토큰만 빠진다 |
| 릴리스 환경으로 옮긴 설치에서 `install.sh`를 다시 실행하면 유닛이 checkout을 가리키도록 되돌아감 | 재현하지 않고 코드로만 확인했다. 설치기의 거절·안내 방식을 정해야 한다 |
| 범례 토글·순서 버튼을 누른 뒤 키보드 초점이 사라짐 | 영향이 작고 다시 그리는 여러 경로를 함께 손봐야 한다 |
| 입력·출력 단가 칸을 비우고 저장하면 이전 값이 그대로 남음 | 필수 값이라 지울 수 없다. 비운 칸에 안내를 띄우는 처리는 하지 않았다 |

## 검증

- `.venv/bin/python -m unittest discover -s tests -q` 613개 통과. 새 검사 18개(`tests/test_review_findings.py` 17개, 방해 금지 요약 1개) 가운데 17개는 수정 전 코드에서 실패하는 것을 확인했다.
- 웹 JS 문법 검사, Node 테스트 45개, 합성 데이터 브라우저 스위트 24개 통과. 개인정보 스위트에 거절된 쓰기 요청이 설정을 비우지 않는지, 개요 스위트에 직접 고른 기간의 끝 날짜를 더했다.
- `tests/verify_record_totals.py`: Devin·Codex·Claude·OpenCode 원본 대조에서 누락·불일치 0건(바뀐 읽기 전용 SQLite 열기 경로 포함). 운영 서비스에는 적용하지 않았다.

## 한도·제공사 영역(둘째 수정)

첫 수정을 병합한 뒤 받은 한도·자원·기타 제공사 영역의 지적 9건 가운데 여섯을 고쳤다(브랜치 `fix/provider-polling`).

- Codex 작업 목록에 식별할 수 없는 항목이 하나 있으면 그 페이지가 실패하고 커서가 처음으로 돌아가, 그 뒤 페이지를 영영 읽지 못했다. 그 항목만 건너뛰고 건수를 상태에 남긴다.
- 실패한 작업 상세를 5분마다 끝없이 다시 요청했다(삭제된 작업 12개면 하루 3,456회). 삭제된 작업(404·410)은 하루에 한 번, 거듭 실패하는 작업은 한 시간에 한 번 요청한다.
- 제공사의 `Retry-After`를 상한 없이 따라, 잘못된 헤더 하나로 조회가 사실상 멈출 수 있었다. 하루로 제한한다.
- Devin 기록의 임시 복사가 도중에 실패하면 대화 내용이 든 부분 복사본이 `/tmp`에 남았다. 실패하면 임시 폴더를 지운다(원본 대조 도구 포함).
- OpenCode Go 응답의 창 하나가 `null`이면 다른 창의 값까지 버렸다. 받은 창은 기록한다.
- Antigravity 언어 서버 포트 탐색이 HTTP가 아닌 응답을 만나면 다른 포트를 시도하지 않고 끝났다. 다음 포트로 넘어간다.

남긴 것:

| 지적 | 남긴 이유 |

| 제공사가 일부 스레드를 응답에서 빼면 스레드 소비 조회가 매번 실패 | 빠진 스레드를 따로 기록하고 재시도 간격을 두는 설계가 필요하다 |
