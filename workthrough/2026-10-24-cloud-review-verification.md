# Codex 클라우드·리뷰 조회 검증과 사용량 화면 통합

## 범위와 기준

- 요청: 클라우드·리뷰의 조회 가능 범위를 검증하고, 승인된 사용량 탭 통합안을 구현·검증하여 운영까지 배포한다.
- 기준: main `f284b67`, 운영 코드 v0.8.1, 설치된 Codex CLI 0.163.0, 개인 Pro 계정의 기존 CLI 인증 및 사용자가 직접 로그인한 웹 화면.
- 독립 `docs/cloud-usage-verification` worktree에서 조사·설계를 기록한 뒤, 승인된 후속 구현은 별도 `feat/codex-consumption` worktree에서 수행한다. 조사·구현·실제 수신·운영 적용을 구분해 기록한다.
- 검증 표본을 만들기 위한 새 모델 작업이나 리뷰를 생성하지 않고 기존 기록을 조회했다. 인증값·대화 본문·원본 응답 전문·계정/작업 식별자·개인별 사용량 수치는 공개 기록에 포함하지 않는다.

## 결론

계정 일별 토큰만 확인할 수 있다는 기존 설명은 확인 범위가 좁았다. 자동 리뷰의 작업 목록, PR 연결, 실행 상태, 모델과 실제 스레드 ID는 조회할 수 있다. 웹이 사용하는 새 사용량 조회에서는 일부 클라우드 작업과 리뷰의 모델별 한도 소비율도 수신했다.

다만 추가로 받은 소비율과 크레딧은 원본 토큰 수가 아니다. 현재 검증한 경로에서 개별 클라우드 작업·리뷰의 입력·출력·캐시 토큰은 확보하지 못했다. 없는 값을 0으로 채우거나 계정 차액을 전부 리뷰에 배정해서는 안 된다.

## 실제 조회 결과

| 조회 | 실제 결과 | 판단 가능한 범위 |
| --- | --- | --- |
| App Server `account/usage/read` | 계정 summary와 일별 토큰 수신 | 계정 총량. 개별 작업·모델·입출력 배분은 없음 |
| 기존 프로필 조회와 공식 RPC 대조 | 반환된 모든 일별 구간과 lifetime 값 일치 | 같은 원본 통계를 중복 합산하지 않음 |
| 기본 `codex cloud list`, 작업 목록 기본/`all`/`archived` | 검사 시점에 빈 목록 | 자동 리뷰 부재를 의미하지 않음 |
| 작업 목록 `task_filter=code_review` | 실제 리뷰 목록과 cursor 수신, 끝 페이지까지 확인 | 작업·PR·생성/갱신 시각·상태 확인 가능 |
| 완료·실패·취소 리뷰 상세 17건 | 모두 HTTP 200. 상세·이벤트 전체에서 토큰 필드를 찾지 못함 | 모델·작업 이력은 확인 가능. 토큰 수신 증거는 아님 |
| 완료 리뷰 15개의 실제 스레드 ID로 공식 RPC 조회 | 모두 `threadUsage=null` | 최근 로컬 스레드만 검사하던 기존 진단보다 범위를 넓혔지만 상세 토큰은 미수신 |
| 구형 `thread_usage/query`, `thread-estimates/query` | 현재 인증으로 HTTP 403 | 이 인증 경로에서 사용 불가. 인증·권한을 바꿔 우회하지 않음 |
| 웹의 `thread_usage/query_v2` | 완료 리뷰 15건 중 4건 `partial`, 11건 `unavailable`; 실패 리뷰도 `partial` | 일부 작업의 한도 소비율·크레딧·모델·추론 강도·속도 수신 |
| 실제 클라우드 세션과 dot 세션의 웹/v2 대조 | 클라우드 표본은 `partial`이며 웹의 반올림된 소비율과 일치. dot 표본은 `unavailable` | 클라우드 전체 또는 모든 dot의 지원 여부로 일반화하지 않음 |
| 웹 일별 분해, 7일·30일 범위 | HTTP 200, `units=percent` | 모델·기능·제품 화면별 한도 소비 분해. 토큰 수가 아님 |
| 플랜 한도 이력 | `coverage_complete=false`, `approximate=true`, `accounting_complete=false` | 불완전한 집계와 근사값으로 취급 |

내부 HTTP 경로는 설치된 클라이언트 또는 실제 로그인된 웹의 요청에서 확인했다. 요청 형식의 검증 오류는 올바른 식별자를 사용한 조회와 구분했고, 정상 응답·미제공·권한 오류를 별도로 판독했다. 내부 경로의 존재나 HTTP 200만으로 공식 외부 연동 지원을 보장하지 않는다.

## 자동 리뷰 목록의 누락 원인

기존 CLI 목록은 리뷰 목록 전체를 대표하지 않는다. 서버는 `task_filter`에 `all`, `current`, `archived`, `code_review`, `security_review`를 구분한다. 실제로 `all`은 비어 있어도 `code_review`에는 기록이 있었다.

- cursor를 따라 마지막 페이지까지 읽었고 task ID 중복과 남은 cursor를 확인했다.
- 목록의 PR 식별 정보와 상세의 PR 연결을 확인했다. 리뷰 실행 횟수와 고유 PR 수는 서로 다른 지표다.
- 상세의 `current_assistant_turn`과 `current_diff_task_turn`은 같은 실행을 중복 표현할 수 있다. 둘을 별도 실행으로 세면 안 된다.
- `thread/started`와 실제 이벤트에서 작업에 속한 스레드 ID를 찾았다. task ID와 실행 스레드 ID는 서로 다른 식별자다.
- `current_assistant_turn.model_version` 등에서 실제 모델을 확인했다. 요청된 모델 이름, UI 선택값, 실제 실행 모델을 구분해야 한다.
- 취소된 표본에는 연결할 실행 스레드가 없었다. 이를 토큰 0의 증거로 쓰지 않는다.

최초 조사 당시 수집기의 `poll_codex_thread()`는 가장 최근 로컬 스레드 하나를 검사했고 리뷰 목록 자동 수집은 없었다. 이 진단만으로 클라우드·리뷰 전체의 조회 가능성을 판단할 수 없다. 0.9.0의 별도 활동·소비 수집은 아래에 기록한다.

## 웹 사용량 분석에서 확인한 추가 데이터

로그인된 설정의 사용량 분석 화면과 그 화면이 호출한 경로를 대조했다.

### 일별 분해

`GET /backend-api/wham/usage/daily-token-usage-breakdown`은 `start_date`, `end_date`, `group_by=day`로 조회했다. 응답에는 다음 값이 있었다.

- `units`, `group_by`, 일별 `date`
- `attribution`: `thread_source`, `turn_trigger`, `model`, `surface`, `value`
- `product_surface_usage_values`
- `models`: `model`, `speed`, `credits`

확인한 계정의 응답 단위는 `percent`였다. URL의 `token`이나 내부 필드명 `credits`만 보고 토큰 수 또는 결제 크레딧으로 해석하면 잘못된다. 반드시 응답 단위와 화면 의미를 함께 보존해야 한다.

자동 코드 리뷰, 보안 검토, dot, 하위 에이전트, 메모리·제목 생성, 승인 검토 등의 출처가 구분됐다. 이들은 기존 계정 차액을 특정 용도로 명명하는 것보다 직접적인 출처 근거다. 하지만 비용·한도 가중치가 다른 소비율을 원본 토큰으로 환산할 수는 없다.

7일 범위에서는 모델·기능 분해 합계를 대조했다. 30일 범위에서는 한 날짜의 기능 분해 합계가 모델·제품 화면 합계보다 작았다. 서로 다른 분해를 더하거나 누락분을 특정 출처에 강제로 배정하지 않는다. 상세 분해의 완전성은 계정 총량 수신과 별도다.

### 작업별 새 조회

`POST /backend-api/wham/usage/thread_usage/query_v2`는 실제 스레드 ID를 `threads` 배열로 보내는 읽기 조회다. 원본 응답에는 다음 값이 있었다.

- `data_as_of`, `comparison_plan`
- 스레드별 `data_status`, `usage_source`
- `five_hour_limit_percent`, `weekly_limit_percent`, `balance_usage_credits`
- `groups`의 모델·추론 강도·속도별 동일한 소비 필드

값이 반환된 표본에서 모델별 주간 소비율 합계는 스레드 합계와 일치했다. 웹의 클라우드 세션 소비율도 같은 값의 반올림 표시였다. `partial`과 `unavailable`을 그대로 구분했으며, 원본 숫자 문자열의 명시적인 크레딧 0과 null을 혼동하지 않았다.

실패한 리뷰에서도 양수 소비율을 받았다. 완료되지 않았다는 이유로 소비량을 0으로 처리해서는 안 된다. 오래된 표본과 최근 표본 모두 미제공 사례가 있어, 단순히 기다리면 모든 기록이 복구된다고 결론내리지 않는다.

이 응답에는 원본 입력·출력·캐시 토큰 필드가 없었다. 구형 App Server의 `threadUsage` 자료형에 토큰 필드가 존재한다는 사실과 새 웹 조회에서 해당 숫자를 수신했다는 주장은 다르다.

## 최초 조사 당시 구현 범위와 후속 작업

- 기존 Codex 계정 일별 토큰과 Claude 클라우드 수집은 운영에서 별도로 유지되고 있다. Claude의 원격 요청·모델 누계 수집을 Codex의 한계와 혼동하지 않는다.
- 이번에 찾은 리뷰 목록·새 작업별 한도 소비·일별 출처 분해는 조회 가능성을 검증한 단계다. 통계 DB나 자동 수집에 새로 연결하지 않았다.
- 후속 구현은 리뷰/PR 활동과 한도 소비를 원본 토큰 통계와 구분해 저장·표시해야 한다. 출처, 단위, 조회 시각, 집계 기준 시각, 구간, `partial`/`unavailable`, 근사·완전성 표시가 필요하다.
- task/turn/thread/PR의 연결을 보존하고 같은 실행의 중복 표현을 제거해야 한다. 실패·취소·여러 시도·페이지 재개를 검증해야 한다.
- 토큰 수를 추가하려면 별도의 원본 토큰 응답이나 관리 가능한 실행 환경의 실제 usage/telemetry 수신이 필요하다. 로컬 exporter 설정만으로 OpenAI가 실행하는 자동 리뷰의 기록이 전달되지는 않는다.
- 조직 Analytics API는 별도의 워크스페이스 관리자 인증이 필요한 경로다. 이번 개인 계정 검증에서 실제 사용 가능하다고 판정하지 않았다.

## 현재 대시보드에 추가하는 구성 검토

아래는 v0.8.1 화면·코드와 대조해 합의한 설계 기준이다. 후속 구현과 실제 검증 결과는 아래 별도 구획에 기록한다.

### 화면 배치

현재 [화면 구조](../llm_usage/web/index.html)는 `한도 / 사용량 / 리포트 / 상태` 네 탭과 별도 설정으로 구성된다. 사용량에는 이미 기간 요약·추이·구성·모델·프로젝트·세션 분석이 있고, 모바일에서는 네 탭이 하단에 고정된다. 이 구조를 유지하면서 사용량 안에 `토큰 분석 / 한도 소비 / 클라우드·리뷰` 전환을 두는 것을 권장한다.

한도 탭은 현재 얼마나 더 사용할 수 있는지와 언제 초기화되는지를, 사용량 탭은 언제·어디에·얼마나 썼는지를 확인하는 곳으로 역할을 정한다. 소비율의 단위가 한도 기준 %라는 사실은 지표 이름과 설명으로 구분할 수 있다. 과거 기능별·모델별 소비 분석을 현재 잔여량 옆에 배치할 이유로 삼지는 않는다.

| 위치 | 추가할 내용 | 표시 기준 |
| --- | --- | --- |
| 사용량 → 한도 소비 | `Codex 한도 소비 분석` | 제공사 기준일별 소비율. 최근 7일/30일, 기능별/모델별 전환 |
| 한도 → Codex 카드 | `소비 분석 보기` 연결 | 사용량의 한도 소비 화면으로 이동. 잔여량을 확인하다 분석이 필요할 때 사용 |
| 사용량 → 클라우드·리뷰 | 기존 토큰 분석과 별도 작업 목록 | 기존 토큰 분석을 기본값으로 유지하고 소비 분석·작업 목록의 필터를 각각 표시 |
| 클라우드·리뷰 → 행 상세 | PR·실행·스레드 연결, 실제 모델, 수신된 한도 소비 | 실행 상태와 소비 데이터 상태를 각각 표시 |
| 상태 → Codex 수집원 | 활동 목록·일별 소비·작업별 소비의 상태와 범위 | 계정 토큰 수집과 개별 토큰 미제공을 계속 구분 |
| 리포트 → 주간 리포트의 후속 확장 | 리뷰 실행 수·고유 PR 수·소비 데이터 제공 범위 | 날짜·집계 범위가 검증된 뒤 추가. 초기 구현의 필수 범위에서 제외 |

사용량의 기존 세션 표에 새 작업을 합치면 토큰이 없는 행이 토큰 순위·요청 수·비용 계산에 섞인다. 화면 맨 아래에 소비 분석과 목록을 추가하면 모바일에서 찾기도 어렵다. 따라서 사용량 안의 전환 버튼으로 토큰 분석·한도 소비·활동 목록을 구분하는 편이 현재 화면에 적합하다. 다섯 번째 전역 탭은 추가하지 않는다.

작업 목록의 개념 배치는 다음과 같다. 대괄호는 조작 요소이며 실제 데이터 예시가 아니다.

```text
한도  [사용량]  리포트  상태
[토큰 분석] [한도 소비] [클라우드·리뷰]

Codex 클라우드·리뷰
생성일 [최근 7일]  종류 [전체]  실행 상태 [전체]
저장소·PR 검색 [                  ]
작업 수 · 고유 PR 수 · 소비 데이터 제공 범위

저장소 / PR 또는 작업 ID | 종류 | 생성일 | 실행 상태 | 소비 데이터 | 상세
상세: 실제 모델 · 주간 한도 기준 소비율 · 원본 토큰 미제공
      조회 시각 · 원본 집계 기준 시각 · 원본 작업/PR 연결
```

PC는 표, 모바일은 `저장소/PR 또는 짧은 작업 ID → 상태 → 수신된 소비율` 순서의 카드로 표시한다. 모델·추론 강도·속도·식별자·시각은 펼친 상세로 옮긴다. 모바일 하단 네 탭과 기존 단축키 1–4는 유지하고, 화면 전환·뒤로 가기·키보드 접근성을 검증한다. 기존 사용량 URL과 저장된 필터는 토큰 분석으로 열리도록 호환성을 유지한다.

### 소비 분석과 작업 상세의 표현

- 사용량 안의 한도 소비 분석은 일별 막대와 상세 표로 시작한다. `기능별`과 `모델별`은 같은 소비를 보는 두 분해 방식이며 서로 더하지 않는다. 제품 화면별 분해는 상세에서 제공한다.
- 기능은 원본 분류에 따라 코드 리뷰, 보안 검토, 클라우드 작업, dot, 하위 에이전트, 백그라운드 작업 등으로 묶고 원본 분류를 상세에 남긴다. 매핑할 수 없는 새 값은 미분류로 남긴다. 일반 작업의 `all` 조회가 모든 활동을 보장한다고 표시하지 않는다.
- 단위는 `한도 소비율 (%)`로 고정해서 명시한다. 일별 응답의 기준 플랜·분모·날짜 경계가 확인되기 전에는 이를 현재 주간 한도 소비나 KST 소비로 명명하지 않는다. `percent`가 아닌 새 단위는 별도 해석을 검증하기 전까지 혼합 표시하지 않는다.
- 처음에는 일별 원본 값만 표시한다. 여러 날짜·초기화 구간·플랜 변경을 단순 합산한 `이번 주 총 소비율`이나 100%로 재정규화한 도넛은 만들지 않는다. 분해 합계가 다르면 `분해 합계 불일치`를 표시하며 차이를 리뷰나 다른 기능에 배정하지 않는다.
- 작업 상세는 수신한 `weekly_limit_percent`를 `주간 한도 기준 소비율`로 표시하고 `partial`이면 `일부 제공`을 붙인다. 5시간 값·크레딧은 원본에서 받은 경우만 별도로 표시한다. 5시간과 주간 비율을 더하지 않는다.
- 작업별 값은 생성일 필터에 포함된 작업에 대해 받은 서버 값이다. 그 값이 선택 기간의 소비량이라는 뜻은 아니다. 원본이 소비 구간을 주지 않으면 `소비 구간 미제공`으로 표시하고 기간 합계를 만들지 않는다.
- 작업 메타데이터의 실행 모델과 소비 응답의 모델별 그룹을 구분한다. 모델을 알게 됐다는 이유로 계정 토큰 차액을 해당 모델에 배분하지 않는다.
- `완료 / 실패 / 취소 / 진행 중`은 실행 상태이고, `일부 제공 / 미제공 / 조회 실패 / 이전 값`은 소비 데이터 상태다. 실패한 작업도 양수 소비가 있을 수 있다. 실행 스레드가 없는 취소 작업도 소비 0으로 단정하지 않는다.
- 카드와 상세의 연결은 같은 작업 식별자가 확인된 경우에만 제공한다. 기능별 일별 소비에서 리뷰 목록으로 이동하더라도 두 화면의 날짜 기준이 다르므로 해당 막대가 목록의 소비 합계라고 표현하지 않는다.

### 필터와 기존 토큰 통계

| 화면 | 적용하는 필터 | 적용하지 않는 필터·해석 |
| --- | --- | --- |
| 기존 토큰 분석 | 기존 기간·간격·분류·지표·비교·범위 | 새 소비율을 토큰·요청 수·가격 환산에 추가하지 않음 |
| 사용량 → 한도 소비 | 독립된 7일/30일, 기능별/모델별 | 토큰 분석의 최근 1시간·프로젝트·비교·누적 설정 |
| 클라우드·리뷰 목록 | 작업 생성일 KST, 종류, 실행 상태, 저장소/PR | 토큰 분석의 모델·프로젝트·비용 필터와 자동 연동하지 않음 |
| 작업 상세 | 선택한 작업의 수신 데이터 | 목록의 생성일 범위를 소비 구간으로 해석하지 않음 |

작업 목록의 기본 기간은 최근 7일이며 30일·직접 지정을 지원하되, 저장된 목록의 실제 수집 범위를 함께 표시한다. 생성일이 없는 항목은 임의 시각을 채우지 않고 `시각 미확인` 조회에서 확인할 수 있게 한다. 최근 1시간을 선택했던 토큰 분석에서 활동 화면으로 이동해도 활동 화면에는 자체 기간이 명시돼야 한다. 일별 소비는 원본 기준일을 보존하고, 원본 시각이 있는 작업의 생성·갱신 시각만 KST로 변환한다.

계정 차액의 숫자는 기존 원본 대조 규칙을 유지한다. 기본 이름 `로컬 미기록`과 사용자가 정한 별칭 옆에 `계정 합계 보완 · 용도 미확인`이라는 성격을 명확히 표시하는 것을 권장한다. 별칭이 자동 리뷰를 뜻하더라도 확인된 리뷰 토큰으로 분류하지 않는다. 새 리뷰 활동 수는 기존 모델 요청 수와도 별개다.

### 수집·저장·API 경계

[현재 수집 루프](../llm_usage/collect.py)는 로컬 기록과 한도를 주기적으로 수집하고, [웹 API](../llm_usage/webapp.py)는 저장된 데이터를 읽는다. 새 경로도 이 구조를 따른다. 다음 명칭과 경로는 구현 제안이다.

1. 별도 `codex_activity` 모듈에서 기존 승인된 Codex 인증을 읽고 작업 목록, 필요한 상세의 식별 메타데이터, 새 작업별 소비 조회, 일별 분해를 수집한다. 계정 토큰 조회·기존 Claude 연동과 실패 처리를 분리한다. 브라우저 로그인 자동화나 새 API 키 발급은 상시 수집의 전제로 삼지 않는다. 인증 만료·권한 거부는 해당 수집원의 상태로 기록한다.
2. 작업 목록, 작업/실행/스레드 연결, 스레드 소비 관측, 일별 소비 분해를 별도 테이블에 보관한다. 기존 `events`, 토큰용 `usage_evidence`, `account_token_buckets`에는 소비율 데이터를 넣지 않는다. 계정 식별 범위와 원본 task/turn/thread ID를 중복 제거 키에 포함한다.
3. 같은 실행의 assistant/diff 표현은 한 번만 기록한다. 같은 PR의 별개 리뷰·재시도는 원본 실행 ID에 따라 보존하며 `리뷰 작업 수 / 실행 수 / 고유 PR 수`를 구분한다. 로컬에서 같은 원본 스레드가 발견돼도 활동 연결만 추가하고 토큰을 다시 합산하지 않는다. 부모·자식의 포함 관계가 불명확한 소비도 합산하지 않는다.
4. 응답 전체와 대화·리뷰 본문은 저장하지 않는다. 식별자·연결·상태·실행 모델·시각·숫자·단위·품질 플래그만 허용 목록으로 추출한다. 작업은 PR/저장소 또는 짧은 ID로 식별하며 프롬프트나 응답 내용을 가져와 제목을 만들지 않는다. 외부 링크는 검증된 HTTPS 작업/PR 링크만 사용한다.
5. 주기·페이지 수·요청 시간을 제한하고, 초기 이력은 여러 수집 주기에 걸쳐 채운다. cursor·수집 범위·완료 여부를 저장하고 중간 실패 후 재개한다. 최근 목록을 겹쳐 읽어 갱신된 작업을 반영하되 반복 수집으로 행을 늘리지 않는다. 응답 정렬이 확인되지 않은 상태에서 오래된 한 항목을 봤다는 이유로 전체 탐색을 완료 처리하지 않는다.
6. 기본 목록/변경 확인은 기존 수집 주기에 맞추되 상세는 신규·변경 작업을 우선하고 소비 미제공 재조회는 간격과 횟수를 제한한다. 일별 분해는 최근 구간을 주기적으로 다시 받아 지연 집계를 갱신한다. 403과 지원 중단을 끝없이 재시도하지 않는다. 수동 갱신도 무제한 전체 이력 조회가 되어서는 안 된다.
7. 예시 API는 `/api/codex/activity`, `/api/codex/activity/<id>`, `/api/codex/consumption`으로 나눈다. 모두 인증된 대시보드의 저장 데이터 조회이며, 화면을 열거나 상세를 펼칠 때 제공사를 직접 호출하지 않는다. 목록은 서버 페이지네이션을 사용한다.
8. [현재 프런트엔드](../llm_usage/web/app.js)의 지연 조회·취소·이전 데이터 표시 방식을 재사용하되 새 요청의 실패가 기존 토큰/잔여량 표시를 막지 않게 한다. 사용량에서 활동 목록이나 한도 소비를 선택했을 때만 필요한 데이터를 읽고, 계정·기간별 캐시를 분리한다. 한도 탭을 여는 것만으로 과거 소비 분석을 불러오지 않는다. 새 데이터의 이전 사본에도 원본 수신 시각과 오래됨 표시를 유지한다.

숫자는 원본 단위와 함께 저장한다. 크레딧 숫자 문자열은 정확한 십진수로 처리하고 `0`, `null`, 키 없음, 파싱 실패를 구분한다. `collected_at`, `data_as_of`, 원본 발생/생성 시각, 적용 구간, `data_status`, `usage_source`, `comparison_plan`, 완전성·근사 플래그를 지원 범위 안에서 보존한다. 필드가 없으면 없는 사실도 보존한다.

### 상태 표시와 구현 순서

상태 화면에는 `활동 목록`, `일별 한도 소비`, `작업별 한도 소비`를 각각 추가한다. 목록 수신 성공은 모든 소비량 확보를 의미하지 않는다. 작업별 `일부 제공 n건 / 미제공 m건 / 식별자 미연결 k건`과 목록 수집 범위를 보여 주고, 이를 `토큰 확보율`이라 부르지 않는다. `data_as_of`가 오래됐으면 방금 조회에 성공해도 최신 집계로 표시하지 않는다. 현재 계정 토큰 수신과 개별 원본 토큰 미제공 상태는 별도로 유지한다.

권장 구현 순서는 다음과 같다.

1. **저장·수집·상태:** 원본 단위, 중복 제거, 페이지 재개와 범위, 실패·미제공·이전 값 처리를 먼저 구현한다. 실제 계정으로 자동 수집 경로를 검증한다.
2. **사용량의 소비 분석과 활동 목록:** 일별 기능/모델 분해, 작업 목록·PR 연결, 일부 작업의 소비 상세를 추가한다. 한도 카드에서 사용량의 소비 분석으로 연결하고 기존 토큰 집계와 필터 회귀를 확인한다. 여기까지를 첫 기능 배포의 범위로 권장한다.
3. **리포트:** 수집 범위와 날짜 의미가 충분히 확인된 뒤 주간 리뷰 실행·고유 PR·상세 제공 범위를 추가한다. 소비율만으로 토큰·실제 비용·구독 가치를 계산하지 않는다.

구현 시 최소 검증은 다음과 같다. 아래는 완료된 검사가 아니라 후속 구현의 수용 기준이다.

- 원본 토큰 합계·기존 사용량 API·모델 순위·비용 환산이 새 소비율 데이터에 의해 바뀌지 않을 것.
- 완료/실패/취소, 부분 제공/미제공, 숫자 0/null, 플랜 변경, 한도 초기화, 일별 분해 합계 차이를 각각 검증할 것.
- cursor 중단/재개, 중복 페이지, 동일 PR의 여러 리뷰, 동일 실행의 중복 표현, 지연 수정, 계정 변경을 검증할 것.
- HTTP 200 안의 미제공, 401/403, 타임아웃, 응답 형식 변경, 오래된 `data_as_of`가 전체 수집 성공으로 덮이지 않을 것.
- 기존 코드 검증과 원본 대조에 더해 PC 1440px, 모바일 390px/320px에서 전환·필터·표/카드·상세·빈 상태·오류·키보드·오프라인 표시를 검증할 것. 합성 fixture와 실제 인증 자동 수집·수동 갱신은 별도 결과로 기록할 것.

## 검증과 문서 관리

실제 계정 조회·웹 표시·완료/실패/취소 표본·페이지 끝·식별자 중복·수치 합계·응답 단위를 검증했다. 합성 fixture를 실계정 수신 결과로 대체하지 않았다. 문서 변경의 diff·공개 파일 검사·상대 링크 검사를 통과했다. 임시 조사 도구와 비공개 메타데이터는 공개 커밋에서 제외하고 제거했으며, 조사에 사용한 브라우저 탭도 닫았다.

통합 검토에서는 현재 HTML·JS·API·수집 루프·저장 구조·사용법 문서를 읽고 운영 대시보드의 한도·사용량·상태 화면을 읽기 전용으로 확인했다. 브라우저 viewport 1440px와 390px에서 접근성 스냅샷과 탭 이동을 확인했다. 해당 브라우저 도구의 스크린샷은 프레임을 받지 못했고 레이아웃 스크립트 조회는 기존 CSP로 거부됐으므로 픽셀 배치·가로 넘침 검증을 완료한 것으로 기록하지 않는다. 당시에는 새 UI가 없어 새 UI 브라우저 회귀 검사를 실행하지 않았다. 검토용 탭을 닫았고 운영 설정·DB·서비스는 변경하지 않았다.

### 문서 PR의 보안 검사와 해결

## 0.9.0 구현과 검증

### 구현

- 사용량 안의 토큰 분석·한도 소비·클라우드 및 리뷰 전환, 독립 필터, 한도 카드에서 분석으로 이동, PC 표·모바일 카드, 키보드·URL 이동을 연결했다. 기존 토큰 분석의 패널 순서와 저장 필터를 유지한다.
- 작업·실행/스레드 연결·개별 소비·일별 분해를 별도 테이블에 저장한다. 기존 토큰 이벤트·누계·롤업을 변경하지 않으며, 계정 차액의 별칭에 용도 미확인 설명을 추가했다.
- 원본 task/turn/thread ID로 중복을 제거하고 부모·자식의 소비를 임의 합산하지 않는다. 실제 복합 실행 ID의 `~` 문자를 지원한다. 작업 상태와 상세 수집/소비 제공 상태를 구분한다.
- 원본 단위, 정확한 크레딧 십진수, 0/null/키 없음/해석 실패, 시각, 플랜·완전성·근사를 보존한다. 과거 응답은 최신 값을 덮지 않고, 미제공으로 바뀌면 이전 관측을 별도 상세로 유지한다.
- 상세 조회 실패가 새 작업의 상세 수집을 막지 않도록 변경 작업·미조회 작업·실패 재시도를 구분하고, 실패 재시도는 오래 기다린 순서로 진행한다. 끝 페이지를 확인한 시각과 현재 이어읽기 상태를 별도로 표시한다.
- 페이지 커서·상세 대기·최근 변경을 이어 읽고 호출 시간과 개수를 제한한다. 인증 거부는 인증 파일 변경을 기다리며, 429 대기는 인증 갱신으로 해제하지 않는다. 다른 제공사와 기존 토큰 수집은 독립적이다.
- 웹 API는 저장된 데이터만 읽으며 provider 조회를 실행하지 않는다. 새 화면의 이전 표시는 페이지 메모리에만 남고 영구 오프라인 캐시에는 넣지 않는다. 조회 조건이 바뀌면 이전 조건의 값으로 대체하지 않는다.

### 실제 수신과 검증 범위

독립 DB에서 실제 CLI 인증으로 새 수집 경로를 실행했다. 일별 30일 응답, 작업 목록과 상세 연결, 개별 스레드의 부분 제공·미제공을 받았다. 부분 제공 값의 상위 소비 필드, 모델별 소비 필드, 모델·추론·속도를 새 원본 응답과 대조해 일치를 확인했다. 새 DB의 기존 토큰 이벤트는 증가하지 않았다.

처음에는 실제 실행 ID의 복합 형식 때문에 상세 연결이 실패했다. 해당 형식을 회귀 fixture에 추가하고 파서를 수정한 뒤 실제 상세 수신과 스레드 소비 연결을 다시 확인했다. 이 결과는 fixture만 통과한 상태와 구분한다.

운영 DB의 읽기 전용 원본 대조에서 기존 Codex·Claude·OpenCode·Antigravity·Devin의 누락·수치 불일치는 없었다. 기존 깨진 기록, 새 append 대기, 모호한 카운터 순서, 원본보다 큰 과거 보존값과 세부값 불일치는 부분 확인으로 유지했다.

새 UI는 합성 Flask API로 실제 Chromium의 1440px·390px·320px에서 전환·필터·페이지·상세·실패/미제공·오래된 값·키보드·뒤로 가기·가로 넘침을 확인했다. 이 단계의 화면 검사는 운영 배포 후 실제 인증 화면·수동 갱신 검사와 별개다.
